## What changed and why

The release path now derives a protected baseline of six checks plus selected-loop requirements. Every protected check needs exact repository/commit, current signed connector evidence, matching retained content hash and gate/artifact bindings. Caller-declared reviewer names cannot approve a release. A separate authenticated Approver/Executive reviews the exact subject, policy and evidence. Self-review is denied; reviews are appended to the existing durable audit journal. Contradictory historical records remain readable but fail closed.

The initial exception policy deliberately permits no waivers. Any declared exception, including a caller's claimed closure, blocks the release. Known exception history for the same tenant/repository/commit cannot be removed by submitting another record or changing workspaces. Remediation needs a new subject and fresh review. This is a conservative operating policy, not implementation of an enterprise risk-acceptance workflow.

The UI shows gates, evidence, hashes, exceptions, authenticated reviewer and rationale. Confirmation binds the reviewer/session and current review history as well as release/evidence identity. It resets when those change. New approvals carry the prior review ID so an old screen cannot silently overwrite a newer rejection. Retries reuse their operation identity; an informed later decision receives a different identity. A long webhook delivery ID exposed a mobile overflow; the grid now permits the card to shrink, and the real browser test checks horizontal overflow.

External LLM output is accepted only under a configured gateway attestation contract. The verifier checks P-256 signatures over literal payload bytes, a fresh nonce, exact request hash, task, provider/model/revision, prompt identity and short validity window. Missing or invalid trust falls back to deterministic behavior. A published test key is rejected by its normalized public-key fingerprint outside the exact development/evaluation/loopback mock exception, even if its marker is removed or renamed. Enterprise LLM timeouts use bounded compiled configuration.

F10 exposed a separate privacy bug: source text labeled internal could downgrade the saved sensitivity classification before transmission. Both saved and proposed classifications must now permit external processing, with consent still required. Negative tests cover sensitive, regulated, restricted and unknown saved classifications; the positive browser fixture explicitly chooses internal data.

The external-effect implementation adds durable aggregate reservations at the actual HTTP tool dispatch boundary. It records explicit units, exact route mappings, cumulative exposure, unknown outcomes, fencing and policy epochs. Unknown external outcomes retain their charge and cannot be blindly reissued. Scope and remaining limitations are detailed under Owner 3; request counts must never be presented as a bound on all financial or customer harm.

Workspace deletion now explains its real scope and requires subject-bound acknowledgment. Removing a workspace is not represented as erasing retained release proofs, audit records, exports, other browser copies, backups or provider data. A failed persistence request remains visible even after the last workspace disappears optimistically. No indiscriminate purge of evidence was implemented.
