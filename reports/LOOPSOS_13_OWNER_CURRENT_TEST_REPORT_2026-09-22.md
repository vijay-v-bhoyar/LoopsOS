## Owner 3 — Enterprise agentic assurance (enterprise-agentic-assurance)

**Assessment: local consequential-effect controls are substantial; hosted concurrency and provider ambiguity remain untested.** Local code and fixtures exercise durable reservations, workflow-scoped idempotency, worker fencing, retry and unknown-response handling, cancellation, compensation, and restart behavior. Other local hardening addresses cross-workflow replay and release-policy epoch mismatch. These are important because a network timeout after an external commit cannot tell the caller whether an effect happened.

Remaining attack paths include two workers acting under stale leases, idempotency keys scoped more narrowly than the business effect, retries after revocation, a successful provider action followed by a lost response, a compensation that itself fails, or the same aggregate budget being reset in another product or tenant. **To close:** run production-equivalent database, RLS, queue, and provider tests with concurrent workers, mixed versions, restarts, lease expiry, duplicate delivery, and cancellation races. ## Owner 4 — Frontier capability assurance (enterprise-frontier-assurance)

It does not tell us whether a newer model can infer hidden goals, exploit an evaluator, or use a tool in an unanticipated way.

A frontier model can change behavior without an obvious API or model-name change. It may infer sensitive context from seemingly incidental cues, expand a narrow objective into a broader one, discover an untested tool sequence, strategically defer until oversight weakens, or exploit correlations in a benchmark. An evaluator can share the same blind spot or provider family as the system under test. No current private holdout campaign against pinned frontier models was run.

**To close:** compare a pinned candidate against a pinned baseline using private holdouts and adversarial, long-horizon, cue-sensitivity, goal-boundary, and tool-composition probes. Analyze judge/evaluator correlation and subgroup performance. Require an explicit model-change trigger, rollback criteria, canary period, and deprecation record. Treat unknown or expired evidence as a visible blocker, not as a positive capability claim.

## Cross-owner failure chains

These are credible compositions to test, not claims that they were observed in production:

1. **Silent model-route change:** a provider alias changes without a human-visible product change (Owners 0, 2, 11); freshness metadata is incomplete; an old benchmark remains green (Owners 1, 4); a fallback shares the route or data dependency; and the user disclosure still describes the previous process (Owners 8, 10).
2. **Ambiguous external action:** a provider commits an effect but the response is lost; retries or restarted workers repeat it; tenant-scoped idempotency misses the aggregate customer impact; revocation fails to stop an old lease; and the dashboard counts only completed records (Owners 1, 3, 5, 7, 12).
3. **Deletion with resurrection:** sensitive data leaves via prompt, retrieval, trace, or fallback; its derivative remains in provider cache, index, log, export, or backup; a restore reintroduces it; and a contaminated label or holdout later treats model output as truth (Owners 2, 9, 11, 12).
4. **Common trust-root compromise:** a signing key, CI identity, evaluator, policy source, or vendor account is compromised or correlated with the deployer; valid-looking evidence authenticates incomplete results; and the supposed independent reviewer shares the same custody or identity system (Owners 3, 5, 6, 7, 10, 11).
5. **Stop without recovery:** new work is blocked but a provider-side asynchronous action or already-leased task continues; no alert reaches a staffed owner; the dead-letter queue has no reconciler; and the affected customer receives neither notice nor remedy (Owners 3, 5, 11, 12).
6. **Selective evaluation:** an operator or model defers difficult cases; abandoned work is absent from the denominator; groups with lower performance are hidden by aggregation; and the reviewer sees only the successful final summary (Owners 1, 7, 10, 12).

Across these chains, the danger is common-mode trust. Several control names do not create defense in depth if they depend on one identity, clock, policy document, evaluator, vendor, database administrator, or observability pipeline. Before treating controls as independent, map their dependencies and test correlated failure.
