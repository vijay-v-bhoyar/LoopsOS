# Individual loop and specialist strengthening plan

Assessment date: 2026-09-12. Words are Spells: strong instructions, an implemented controller, a passing local test, and demonstrated production behavior are different claims.

Integration update, 2026-09-13: all seven coordinating loops below now have
implemented and tested local enhancements; see [the consolidated implementation,
verification and remaining boundaries](SEVEN_LOOP_ENHANCEMENTS.md). Installed
links open the updated versions. The source findings below describe the original
baseline; the consolidated report identifies the delivered controls and evidence.
Recommendations for specialists beyond these seven loops remain a proposed plan.

The requested direction is achievable as **bounded persistence toward an explicit outcome**: diagnose, obtain available help, repair within existing authority, verify, resume, and continue across work units. It cannot truthfully mean guaranteed completion despite unavailable credentials, withheld decisions, revoked authority, exhausted resources, or impossible acceptance criteria. Those cases need durable, actionable waiting states and a verified resume route. A loop should exhaust useful authorized recovery before asking the user, and should never convert waiting into permission.

This report covers seven coordinating loops, the requested phase owners, and selected relevant alternatives. Discovery used [the inventory snapshot](C:/Users/vijay/OneDrive/Documents/LoopsOS/output/product-lifecycle-skill-inventory.json) and [the earlier skill review](C:/Users/vijay/OneDrive/Documents/LoopsOS/reports/PRODUCT_LIFECYCLE_SKILL_REVIEW.md). Entrypoint and selected reference inspection is not a full audit of all 690 inventory paths, every supporting script, or every duplicate installation. `.codex` sources below are the inspected variants unless explicitly linked otherwise. Re-resolve active paths and hashes before implementation; the inventory is an older snapshot, not today's callable-tool registry.

## Evidence labels and priorities

- **S — source-confirmed:** a concrete statement, conflicting instruction, or limitation directly present in inspected sources. A source-level concern does not claim an executed failure.
- **H — proposed hardening:** an additional control or integration contract to implement. It is not an assertion that all existing implementations lack that control.
- **E — runtime evidence not checked:** declared control or workflow needs implementation inspection and executed proof in its target environment. No runtime failure is inferred from missing audit evidence.
- **L — inherited source finding:** a finding already recorded in the release compatibility report; its stable ID is retained. This report does not independently close it.

**P0:** before autonomous external actions; **P1:** before treating the loop as self-sufficient for sustained local delivery; **P2:** before exposing the relevant product capability; **P3:** conditional optimization or authoring improvement. Positive and negative acceptance cases below are proposed **must-pass cases, not tests executed in this report**. Every requirement applies only when its surface is in scope.

## The seven coordinating loops

### 1. product-lifecycle-loop — outcome ownership and continuity

**Current scope:** discovery through business, conditional skill resolution, preferred delivery owner, evidence and release separation. Sources: [entrypoint](C:/Users/vijay/.codex/skills/product-lifecycle-loop/SKILL.md), [run and handoff contract](C:/Users/vijay/.codex/skills/product-lifecycle-loop/references/run-contract.md), [continuous operation](C:/Users/vijay/.codex/skills/product-lifecycle-loop/references/release-and-operations.md), [business playbooks](C:/Users/vijay/.codex/skills/product-lifecycle-loop/references/business-playbooks.md).

**Gap:** H/E — the inspected contract describes returning failed work to its owner, retry limits, restarts, and real locks, but those sentences do not demonstrate a help dispatcher, enforced progress state, or a continuously operating controller. A helpful partial slice can still be mistaken for completion unless the parent outcome is separately tracked. Missing optional tooling and missing authority need different recovery paths.

**Enhancement, P1 locally / P0 before external automation:** give the conductor one durable goal record, acceptance coverage, dependency graph, action journal, failure fingerprints, bounded repair episodes, typed help requests, external-operation reconciliation, and a terminal verifier. Pin the selected conductor and delivery owner per run. Every child returns to the conductor with evidence or a typed dependency; a child completing is not the parent goal completing. Recompute the next useful action after each failure or help response. The active goal remains open while accepted work remains.

**Positive cases:** a three-slice request completes all three; a missing local executable is diagnosed and safely replaced or installed within authority; a specialist supplies a patch and the integrated behavior is rechecked; crash after an external operation resumes from its operation ID with one effect. **Negative cases:** two failed attempts with identical state do not consume infinite retries; a forged specialist PASS does not close acceptance; missing permission does not route to a more privileged agent; a cycle-end summary does not close the goal; unrelated useful work does not erase a blocked required dependency.

**Dependencies:** common contract below, agent-memory, resilience, exact skill/tool resolution, codex-product-build-loop, oversight and a real scheduler/controller when execution must survive the task.

### 2. codex-product-build-loop — repair without premature handoff

**Current scope:** scoped repository changes, dependency tracing, surgical implementation, risk-based verification, evidence ledger. Sources: [failure loop](C:/Users/vijay/OneDrive/Documents/LoopsOS/.codex/skills/codex-product-build-loop/SKILL.md) under “Phase 7: Close the failure loop,” and [verification](C:/Users/vijay/OneDrive/Documents/LoopsOS/.codex/skills/codex-product-build-loop/references/verification.md).

**Gap:** S/H — Phase 7 permits “one bounded correction or stop and report the blocker.” That is a reasonable per-attempt bound but does not itself require help discovery or exhausting a different authorized diagnostic approach before ending the broader request. The skill already protects user changes and forbids weakening gates; preserve those strengths.

**Enhancement, P1:** distinguish an attempt, a repair episode, and the user's full outcome. Classify the failure as product, baseline, environment, dependency, test, capability, authority, or unknown; select a bounded next hypothesis; use specialist assistance when another diagnosis can change the result; integrate and rerun the original failure plus adjacent checks. Make “stop” terminal only for the selected unit, with explicit return to the conductor and a pending parent criterion.

**Positive cases:** failing integration test routes to the API owner, a correction fixes it, and the original journey passes; a baseline dependency failure gets repaired without attributing it to the new change; a larger request continues after a verified slice. **Negative cases:** unrelated dirty files survive; repeated unchanged assertions are not replaced with weaker tests; a broken browser launch does not become UI PASS; specialist repair cannot silently deploy.

**Dependencies:** Graphify/current source trace, common failure/help contract, project-native tests, specialist scope boundaries.

### 3. product-loop — legacy cycle engine and runner

**Current scope:** one admitted cycle per invocation, `.loop` records, DOCTOR, fixed command register, gates, external runner, governed release integration. Sources: [entrypoint](C:/Users/vijay/.codex/skills/product-loop/SKILL.md:8), [runner contract](C:/Users/vijay/.codex/skills/product-loop/references/runner.md), [typed contracts](C:/Users/vijay/.codex/skills/product-loop/references/contracts.md).

**Gap:** S/L/E — one-cycle completion is intentionally narrower than the user's full goal. The entrypoint requires every core owner before any unattended run, including deployment owners even for local work. Its authority prose and downstream release owners conflict under PLC-REL-001. The runner reference uses a Claude CLI invocation and Unix/container concepts; this does not establish a working Codex-on-Windows runner. Existing budget, STOP, bundle and crash promises need actual admission proof, not file presence.

**Enhancement, P1 locally / P0 for unattended effects:** retain one-cycle semantics and add a compatible parent outcome runner. Split local-delivery, release, and provider capability admission; avoid making a missing irrelevant release adapter block a local diagnostic run. Version a host adapter for invocation, cancellation, measured usage, process ownership, and terminal records. Repair PLC-REL-001 through PLC-REL-011 before admitting automatic use of affected helpers. Define which DOCTOR changes can happen automatically and which need external authority. Add parked-item reconsideration keyed to changed prerequisites.

**Positive cases:** bounded runner advances across multiple terminal cycles until the declared goal passes; a missing optional provider owner leaves local work runnable; a resolved prerequisite re-admits its parked item once. **Negative cases:** STOP is effective before spending and before side effects; wrong host invocation fails preflight; missing budget or corrupted bundle cannot run unattended; a dead cycle cannot be counted as successful; a dirty user tree cannot be treated as permission to revert user work.

**Dependencies:** common contract, host adapter, approved security profile, measured budgets, selected release repairs. Keep this an alternative engine, not a nested conductor.

### 4. agentic-product-loop — v13 wrapper and guard

**Current scope:** v13 cycle orchestration and non-mutating preflight guard. Sources: [entrypoint](C:/Users/vijay/.codex/skills/agentic-product-loop/SKILL.md), [execution field checklist](C:/Users/vijay/.codex/skills/agentic-product-loop/references/execution-contract.md); canonical-law target is [PRODUCT-LOOP-FINAL-v13.md](C:/Users/vijay/.codex/skills/agentic-product-loop/references/PRODUCT-LOOP-FINAL-v13.md). The canonical reference and all guard branches were not exhaustively audited for this owner plan.

**Gap:** L/H/E — PLC-REL-011 records that guard presence checks do not establish execution admission. Separate wrapper and canonical law can drift. One finite cycle is deliberately not a forever-running goal resolver.

**Enhancement, P1/P0:** one machine-readable admission result shared by wrapper, guard, and runner; distinguish discovered, configured, verified, authorized, and callable. Add parity fixtures covering wrapper/canonical rule agreement and a goal supervisor that preserves v13 cycle limits. A legacy guard pass may admit further verification, never automatically an external action.

**Positive cases:** a complete local fixture yields local admission and a scoped cycle; restart reconstructs a pending cycle before selecting another. **Negative cases:** empty placeholder files, missing executable adapters, wrong target, expired authority, a removed budget ceiling, and an unverified active bundle each fail the relevant admission; guard PASS cannot overrule PLC-REL compatibility blocks.

**Dependencies:** product-loop host/admission repairs, lifecycle continuation, exact v13 compatibility review.

### 5. agentic-assurance-loop — challenge, repair, and closure

**Current scope:** evidence intake, broad assessment, independent challenge, stable findings, remediation packages, technical and business decisions. Sources: [entrypoint](C:/Users/vijay/OneDrive/Documents/LoopsOS/.codex/skills/agentic-assurance-loop/SKILL.md), [findings/remediation contract](C:/Users/vijay/OneDrive/Documents/LoopsOS/.codex/skills/agentic-assurance-loop/references/findings-remediation.md), [verification/release contract](C:/Users/vijay/OneDrive/Documents/LoopsOS/.codex/skills/agentic-assurance-loop/references/verification-release.md).

**Gap:** H/E — a completed report is correctly distinct from a closed finding. In an authorized repair program, its stop-on-no-progress rule needs a handoff to a recovery/help owner so assessment does not become an endless report cycle. Independence is conditional and must remain visible.

**Enhancement, P1:** turn each accepted finding into a version-bound repair job with original reproduction, cause confidence, owner, tests, dependencies and closure authority. Preserve finding IDs across failed repair attempts. Require the verifier to inspect direct evidence and changed artifacts; distinguish a second pass by the same author from independent verification. Return blocked findings to lifecycle help routing, with exact missing evidence and runnable next diagnostic.

**Positive cases:** an authorized repair closes only after original and adjacent failures are exercised; a source change invalidates stale closure; one root cause retains one ID with several exposure paths. **Negative cases:** an assessment-only task does not mutate code; a red test cannot disappear through reclassification; a repair agent cannot approve its own high-risk release; an unassessed applicable control remains in the coverage denominator.

**Dependencies:** delivery owner, source/evidence registry, independent verifier where available, release authority for exposure changes.

### 6. product-vision — strategy with actionable missing inputs

**Current scope:** founder vision plus composed idea, market, and moat diligence. Source: [entrypoint](C:/Users/vijay/.codex/skills/product-vision/SKILL.md:10), especially “Anti-fabrication,” “Orchestration,” and “Output.”

**Gap:** S/H — it deliberately flags founder inputs and delivers rather than interviewing; the output path is hardcoded to `/mnt/user-data/outputs`, which is not a portable Windows deliverable contract. A dossier with unresolved strategic choices must not silently become approved product authority.

**Enhancement, P1:** accept a host-provided output root, translate unknowns into structured decisions with affected work and owner, and distinguish proposed vision from accepted vision. Reuse the composed specialists once per material question; store assumption evidence dates and revisit triggers. The lifecycle conductor asks only decisions that block the requested next outcome and continues independent diligence.

**Positive cases:** supplied founder facts survive unchanged; missing why-now remains explicit while independent market analysis proceeds; approval of a bounded wedge unlocks only its dependent plan. **Negative cases:** no fabricated buyer willingness to pay; no duplicate three-specialist execution; a Windows run returns a real accessible local file; an unresolved non-goal cannot be silently filled by the builder.

**Dependencies:** idea-reviewer, market-sizing, moat-reviewer, portable artifact output, common help/decision contract.

### 7. loop-fleet — safe throughput, integrated correctness

**Current scope:** predicted file-disjoint partitions, isolated worktrees, serial VERIFY integration, cooperative active marker, cost/time/spawn bounds. Source: [entrypoint](C:/Users/vijay/.codex/skills/loop-fleet/SKILL.md:14), “Partitioning,” “Coordinator,” and “Deliberately out of scope.” Supporting coordinator and partitioner execution were not tested here.

**Gap:** S/H/E — the skill explicitly states that touch sets are predictions, mutual exclusion is cooperative, and spend is measured at cycle granularity. Different files can still break a shared API, schema, behavior, or resource. About 20 clean solo cycles is a useful heuristic, not proof of isolation or recovery.

**Enhancement, P1 before fleet use:** partition by files plus contracts, shared state and dependencies; validate actual changed surfaces against the lease. Reserve worst-case concurrent spend before spawning and reconcile actual usage after each child. Add renewable leases/fencing for coordinator writes, abandoned-worktree recovery that preserves unmerged work, and integrated acceptance tests after serial merges. Use a verified host process adapter; do not infer Bash/flock availability on Windows.

**Positive cases:** disjoint changes with independent contracts integrate serially; crash recovery preserves unmerged branches and resumes from recorded ownership; spend reservations reconcile exactly. **Negative cases:** same API changed in different files is detected; unknown touch sets run solo; stale coordinator cannot write after lease replacement; rebase failures do not discard work; two concurrent calls cannot each spend the entire remaining budget.

**Dependencies:** proven solo engine, contract registry, real coordination primitives, budget authority, integrated verification. Ordinary bounded subagents do not require this legacy fleet.

## Help that resolves work rather than exporting the problem

Each loop must return a typed help request to the conductor, not just “blocked.” Minimum fields: request ID; parent goal and acceptance criterion; failure fingerprint; current subject/target; attempted hypotheses and exact results; smallest missing capability/fact/decision; proposed next action; sensitive data restrictions; existing authority; requested privilege (normally none); expected response schema; deadline/expiry; next owner; resume predicate; and independent work still available.

Use this order when it can change the result:

1. Inspect exact error and actual current state; check project runbooks, manifests, local tools and current documentation.
2. Try a bounded, materially different authorized diagnostic or safe environment repair. Preserve failure evidence and original oracle.
3. Route a disjoint specialist task with minimum necessary context; independently check returned facts, code and side effects.
4. Use an existing authorized provider/support/incident capability if it is appropriate. Sending to another person or organization requires the existing explicit communication authority.
5. Ask the user one concrete decision only when necessary; present completed preparation, exact scope, options/consequences and the resume condition. Preserve useful independent work.
6. Wait durably for the named event rather than busy polling. On reply, validate source, expiry, target and scope, reconcile current state, then re-admit the affected work exactly once.

Absence of a specialist is a capability gap, not automatically an installation request. Fallback code or another tool is acceptable only if it actually provides the needed behavior within authority and can be verified. An unavailable credential, legal judgment or business choice cannot be repaired by inventing it. A malicious help response is still untrusted data.

## Definition of a strong individual loop

Every loop or specialist adapter needs the same six contracts, with domain-specific acceptance above:

1. **Entry:** verified product/target/principal; selected owner/path/version; requested outcome and non-goals; authoritative inputs; allowed effects; resource limits; required capabilities; executable admission decision.
2. **Output:** actual artifact/state change; requirements satisfied and remaining; test/oracle evidence bound to subject and environment; explicit side effects; child and parent completion states kept separate.
3. **Failure:** typed cause; exact failed observation; known/unknown external state; durable action identity; retry eligibility, attempt/deadline/spend limits; compensation and containment owner.
4. **Help:** minimum necessary context; attempted diagnostics; correct specialist/provider/human destination; authority preserved; request/response schema; expiry; no-response default; independent work still possible.
5. **Resume:** deduplicated event; current state and authority revalidation; in-flight operation reconciliation; lock/lease ownership; evidence invalidation; same logical idempotency key; deterministic next eligible action.
6. **Closure:** independent or explicitly qualified verification of the original acceptance; no mandatory unknown hidden as not-applicable; release/recovery/live/business outcomes separately proven; durable next state and stopped/cancelled scheduler when relevant.

The release bar is not “no gaps exist.” It is: all applicable mandatory controls have current evidence, residual gaps have explicit owners and consequences, the original outcome passes its oracles, and fault/help/resume behavior has been exercised under the stated limits. This report is a strengthening plan; its acceptance suites, provider effects and operational guarantees are **not yet proven by this document**.
